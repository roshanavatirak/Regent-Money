      Proposed

      Server decides what to show, the app decides who sees it

      The 10 illustrations stay bundled in the app, so no images are downloaded. Everything else (text, colour, order, button action, targeting rule, schedule, on/off) comes from the backend as a published release. The rule is checked on the phone, so balances and SMS data never leave the device.

      Admin edits a draftKept as one JSON row. Saving the draft is one UPDATE. Users see nothing yet.
      Publish = one transactionInserts immutable release v13 and the audit log in Postgres, then swaps the server's in-memory copy. Nothing is deleted, so there is no invalidation race.
      Version rides alongCalls the app already makes (/app/version-check at launch, /sync incl. its 304s) get a header X-Home-Cards: 13. Zero extra requests.
      Fetch only on changePhone has v12 and sees 13: one GET /home-cards/13, served from memory, cached forever because v13 never changes.
      Phone filters & rendersChecks platform, schedule and rule against local data, fills {{tokens}}, renders the carousel.
      Why this design

      The version number is the cache key

      A release never changes after it's published, so nothing ever needs invalidating. Publishing just moves the pointer from 12 to 13. A phone that already has 13 never asks again, and a phone with 12 asks exactly once.

      Architecture decision

      No new Redis. Three cache layers, each cheaper than the one behind it

      This is the pattern behind remote-config services such as Firebase Remote Config and LaunchDarkly: an immutable, versioned config, a tiny "current version" signal, and clients that cache locally and download only on change.

      Options considered

      OptionVerdictWhy
      Redis cache-aside, 30-day TTLRejectedLoad grows with every app open; free cap gone in ~10 days; stale-refill race.
      New dedicated Upstash for cardsNot needed nowWith one server, memory is the cache. Use the existing Redis only if you run 2+ instances (below).
      Firebase Remote ConfigGood alternativeFree and CDN-backed, but needs the React Native Firebase native SDK (not in the app today) and its publish API from the backend. More moving parts than this feature needs.
      Static JSON on a CDN (Supabase Storage)Upgrade pathIf card fetches ever become a measurable load, publish also uploads home-cards/v13.json; the header points to it and Render serves nothing.
      Version pointer, memory + PostgresChosenZero steady-state cost, no new service, no invalidation logic, survives Render sleeping and restarts.

      Limits that keep anything from running out

      • Single-flight load: on boot or a memory miss, concurrent requests share one Postgres query instead of each running their own.
      • Jittered fetch: a phone that sees a new version waits a random 0–30 s before downloading, so a publish never becomes a spike.
      • Throttle: /home-cards/:version sits behind the existing throttler (10 per user per minute); publish is limited to 1 per 30 s.
      • Backoff: if the fetch fails, the phone keeps its cached cards and retries on the next header, never in a loop.
      • Size caps: 12 cards per release, 70/22-character text, release under 16 KB, last 20 releases kept.
      • Fails safe: server down or Postgres down means phones keep showing their cached cards, or the bundled six.

      Database (Postgres, core schema)

      -- one row: the admin's working copy
CREATE TABLE core.home_card_draft (
  id          smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  cards       jsonb NOT NULL,      -- same shape as a release
  rev         int  NOT NULL DEFAULT 0,  -- stops two admins overwriting each other
  updated_by  uuid REFERENCES core.users(id),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

-- immutable published snapshots; never updated, only inserted
CREATE TABLE core.home_card_releases (
  version       int PRIMARY KEY,   -- the cache key
  cards         jsonb NOT NULL,
  note          text,
  published_by  uuid REFERENCES core.users(id),
  published_at  timestamptz NOT NULL DEFAULT now()
);

-- server start: the only read users ever cause
SELECT version, cards FROM core.home_card_releases
ORDER BY version DESC LIMIT 1;          -- PK index, <1 ms

-- save draft (optimistic lock)
UPDATE core.home_card_draft SET cards=$1, rev=rev+1, updated_by=$2, updated_at=now()
WHERE id=1 AND rev=$3;                  -- 0 rows = someone else saved first

-- publish, in one transaction
INSERT INTO core.home_card_releases(version,cards,note,published_by)
SELECT COALESCE(MAX(version),0)+1, $1, $2, $3 FROM core.home_card_releases
RETURNING version;                      -- PK clash = concurrent publish, retry
DELETE FROM core.home_card_releases WHERE version <= $v - 20;  -- keep 20 for rollback

      Per-card rows aren't needed: the admin always saves and publishes the whole list, which is under 10 KB. Ship as a TypeORM migration next to 1730000007000-AddServerChangedAt.ts (the app runs with synchronize: false).
